ВВЕДЕНИЕ
В современных условиях развития рынка недвижимости автоматизация процессов
учёта и управления объектами строительства становится важной задачей для застройщиков.
Ручное ведение данных об объектах недвижимости, фиксация продаж, формирование
договоров купли -продажи и отслеживание статусов сделок являются трудоёмкими
процессами, подверженными ошибкам и не обеспечивающими необходимой
оперативности. В связи с этим разработка автоматизированного рабочего места (АРМ)
застройщика является актуальной задачей, направ ленной на повышение эффективности
управления объектами недвижимости и качества обслуживания клиентов.
Целью курсового проекта является разработка и тестирование информационной
системы для автоматизации хранения и учёта информации об объектах недвижимости,
управления фотографиями и строительной документацией, ведения статусов объектов и
формирования договоров купли-продажи. Для достижения поставленной цели необходимо
провести анализ предметной области и сформулировать требования на основе технического
задания, разработать архитектуру приложения, обеспечивающую масштабируемость,
надёжность и безопасность, реализовать ролевую модель доступа для различных категорий
пользователей, а также выполнить тестирование разработанной системы, включая
функциональное, интеграционное и UI-тестирование.
Объектом исследования является процесс автоматизации деятельности застройщика
по учёту и управлению объектами недвижимости. Предметом исследования выступают
методы и технологии проектирования, разработки и тестирования клиент -серверных
информационных систем. Разрабатываемая система предназначена для централизованного
хранения и обработки данных об объектах недвижимости, их фотографиях, строительной
документации, договорах купли-продажи, а также для управления договорами и ролями.
Практическая значимость работы заключается в создании информационной
системы, способной повысить эффективность работы застройщика, упростить обработку
данных об объектах недвижимости, автоматизировать формирование договоров купли -
продажи и обеспечить прозрачность учёта имущества.

ВИД АВТОМАТИЗИРУЕМОЙ ДЕЯТЕЛЬНОСТИ

Необходимо разработать приложение, предназначенное для автоматизации
хранения и учёта информации об объектах недвижимости.
Основными функциями автоматизированного рабочего места являются:
– добавление, редактирование информации о продаваемом объекте недвижимости;
– добавление фото строительного объекта недвижимости (возможно прикрепление
нескольких фото);
– изменение фото строительного объекта недвижимости;
– удаление данных об объекте недвижимости;
– поиск информации об объектах недвижимости: поиск определяется видом
недвижимого имущества;
– добавление строительной документации по объекту (схема, план застройки);
– удаление строительной документации по объекту недвижимости;
– просмотр всех имеющихся объектов недвижимости;
– установление статуса объекту недвижимости (продан, продажа и т.п.);
– изменение статуса объекта недвижимости (продан, продажа);
– задавать не только основную цену, но и скидочную цену объектов недвижимости;
– распечатывать договор купли-продажи объекта недвижимости (Word (.docx)).

По каждому объекту недвижимости заносится:
– Тип объекта;
– Общая площадь;
– Отделка;
– Материал стен;
– Этаж;
– Цена;
– Фотографии, схемы;
– И т.п.

Пользователи информационной системы:
– незарегистрированные пользователи;
– зарегистрированные пользователи;
– менеджеры;
– администраторы.

Незарегистрированные пользователи могут только просматривать информацию о
строительных объектах и строительной документации.
Зарегистрированные пользователи могут также просматривать информацию о
договорах с застройщиком.
Администраторы ведут сопровождение (заполнение, редактирование информации о
строительных объектах и объектах недвижимости).
Менеджеры ведут фиксацию продажи объектов недвижимости.
2. АНАЛИТИЧЕСКАЯ ЧАСТЬ
2.1. Цели, функции и задачи системы
Актуальность разработки автоматизированного рабочего места застройщика
обусловлена необходимостью повышения эффективности управления объектами
недвижимости в условиях постоянного роста рынка строительства и увеличения объёма
данных о продаваемых объектах. В процессе работы застройщика ежедневно выполняются
операции, связанные с регистрацией новых объектов недвижимости, ведением справочника
типов объектов, оформлением договоров купли -продажи, изменением статусов сделок и
контролем доступа пользователей к раз личным функциям системы. При использовании
ручного учёта или разрозненных программных решений возрастает вероятность ошибок,
усложняется контроль данных, теряется прозрачность действий и увеличивается нагрузка
на сотрудников.
Основной целью разрабатываемой  системы является создание единого
программного комплекса, который позволит автоматизировать основные процессы учёта
объектов недвижимости, обеспечить централизованное хранение информации и повысить
удобство взаимодействия между администраторами, менеджера ми, зарегистрированными
и незарегистрированными пользователями. Предполагается, что система будет
обеспечивать безопасную обработку данных, поддержку ролевой модели доступа и
возможность дальнейшего расширения функциональности.
Информационная система будет включать несколько основных компонентов. Одним
из компонентов станет API-бэкенд с поддержкой версионирования API (v1 и v2). API будет
использоваться для обработки запросов, взаимодействия с базой данных, реализации
бизнес-логики и поддержки механизмов аутентификации и авторизации пользователей. Для
API предполагается использование автоматической документации Swagger/OpenAPI.
Вторым компонентом системы станет полнофункциональное веб-приложение, реализуемое
на основе Django. Веб -приложение будет использовать  шаблоны, формы и
административную панель для взаимодействия с пользователями. Получение и обработка
данных будут выполняться через REST API, что позволит разделить пользовательский
интерфейс и серверную бизнес -логику. Для хранения информации предполагаетс я
использование клиент -серверной базы данных PostgreSQL, обеспечивающей
централизованное хранение данных об объектах недвижимости, пользователях, договорах
купли-продажи, фотографиях, строительной документации .
К основным функциям системы относятся регистрация и авторизация
пользователей, управление ролями и правами доступа (администратор, менеджер,
зарегистрированный пользователь, внешний пользователь), хранение и обработка данных
об объектах недвижимости и их характеристиках, управление ф отографиями и
строительной документацией объектов, учёт договоров купли -продажи с возможностью
формирования документов Word (.docx), ведение истории договоров пользователей, а
также администрирование системы (управление пользователями и справочниками).
Для достижения поставленной цели необходимо решить следующие задачи:
выполнить анализ предметной области и определить требования к информационной
системе учёта объектов недвижимости, разработать архитектуру приложения и структуру
взаимодействия между веб -приложением, API и базой данных, реализовать механизмы
аутентификации, авторизации и разграничения прав доступа, разработать основные модули
системы и REST API, а также выполнить тестирование основных функций и компонентов
приложения.
2.2. Описание предметной области системы
Предметная область проекта охватывает деятельность застройщика в части учёта
объектов недвижимости, управления их фотографиями и строительной документацией,
ведения договоров купли -продажи и контроля взаимодействия между пользователями
системы. Анализ предметной области выполняется не только как описание сущностей базы
данных, но и как исследование основных процессов работы застройщика, требующих
автоматизации.
В основу проектирования системы предполагается положить последовательность
основных этапов взаимо действия пользователей: регистрация объекта → добавление
фотографий и документации → установка статуса и цены → оформление договора купли -
продажи → скачивание договора. Именно данный процесс определяет состав сущностей и
взаимосвязей внутри системы. Основная за дача проектирования заключается в
обеспечении непрерывности хранения и обработки данных на всех этапах работы
пользователей с приложением.
С точки зрения информационных потоков в системе предполагается выделение
следующих основных объектов предметной области:
– объект недвижимости (тип, площадь, отделка, материал стен, этаж, основная и
скидочная цены, статус, адрес, описание);
– тип объекта недвижимости (квартира, дом, коммерческая площадь, и т.д.);
– фотография объекта (файл, описание, дата загрузки, ссылка на объект);
– строительная документация (схема, план застройки, наименование, тип, дата
добавления);
– договор купли -продажи (данные покупателя и продавца, стоимость, дата, статус,
примечания);
– пользователь системы (учётные данные, роль и права доступа);

Выделение именно этих сущностей обусловлено спецификой работы застройщика и
необходимостью централизованного хранения информации об объектах недвижимости и
фактах совершения сделок.
В предметной об ласти предполагается использование нескольких ролей
пользователей:
– администратор — полное управление системой, пользователями и объектами
недвижимости;
– менеджер — фиксация продажи объектов недвижимости, управление договорами;
– зарегистрированный пользовател ь — просмотр информации о договорах с
застройщиком;
– незарегистрированный пользователь — ограниченный доступ к общедоступной
информации об объектах и строительной документации.
Такое разделение ролей позволит ограничить доступ пользователей только к тем
функциям и данным, которые относятся к их обязанностям. Для реализации данного
механизма предполагается использование ролевой модели доступа (RBAC) на основе JWT-
токенов.
Для форм ирования структуры проекта предполагается изучение существующих
информационных систем управления недвижимостью, типовых CRM -систем для
застройщиков и порталов объявлений о продаже недвижимости. Также будут
анализироваться процессы взаимодействия между сотр удниками и клиентами, порядок
оформления договоров купли -продажи и принципы хранения данных об объектах.
Ключевым критерием отбора исходных данных является их практическая значимость для
работы системы.
При отсутствии единой информационной системы в работе застройщика возникают
типовые проблемы:
– разрозненное хранение информации об объектах и документации;
– сложность отслеживания статуса сделок и изменения цен;
– необходимость повторного ручного ввода данных при формировании договоров;
– ошибки при регистрации объектов и учёте покупателей;
– отсутствие единого личного кабинета покупателя.
Автоматизация данных процессов позволит сократить количество рутинных
операций и повысить эффективность работы застройщика.
2.3. Определение пользователей системы
Целевой аудиторией системы являются администраторы застройщика, менеджеры
по продажам, зарегистрированные пользователи (потенциальные покупатели) и
незарегистрированные пользователи, так как именно эти категории ежедневно
взаимодействуют с данными об объектах нед вижимости, договорах и документации.
Интерфейс системы должен быть адаптирован не под технических специалистов, а под
пользователей, которым необходимо быстро выполнять рабочие операции и получать
доступ к нужной информации без сложной навигации.
Основной сценарий использования системы строится по принципу минимального
количества действий: авторизация → выбор раздела → работа с объектами или договорами
→ сохранение изменений → просмотр результатов. Навигация системы должна быть
организована по логике работы  пользователей, а не по внутренней структуре модулей
приложения.
Для системы предполагается использование ролевого интерфейса (role -based UI).
Каждый пользователь будет видеть только те разделы и функции, которые относятся к его
роли:
– администратор — полное управление объектами недвижимости, фотографиями,
строительной документацией, статусами, ценами, договорами и пользователями;
– менеджер — фиксация продаж, управление договорами купли-продажи и изменение
статусов объектов;
– зарегистрированный пользователь — просмотр своих договоров с застройщиком и
информации об объектах;
– незарегистрированный пользователь — просмотр общедоступной информации об
объектах недвижимости и строительной документации без персональных данных.
В рамках проектирования предлагается разра ботка UML-диаграммы прецедентов.
На диаграмме будут отражены основные участники системы: администратор, менеджер,
зарегистрированный и незарегистрированный пользователь, а также варианты их
взаимодействия с системой.
Рисунок 1 — Диаграмма прецедентов
2.4. Проектные решения по реализации внутренней архитектуры приложения
В проекте планируется использование двухслойной архитектуры: Django
применяется как web-слой пользовательского взаимодействия, а FastAPI — как сервисный
слой бизнес -логики и REST API. Такое решение позволяет разделить ответственность
между интерфейсной частью и обработкой данных: web -слой отвечает за отображение
страниц, формы, маршрутизацию и взаимодействие с пользователем, а API -слой — за
обработку бизнес-операций, проверку ролей, валидацию данных и работу с базой данных.
Взаимодействие компонентов системы организуется по следующей схеме:
пользователь → Django web-приложение → FastAPI REST API → PostgreSQL. Внутренняя
архитектура проекта строится на основе модульного подхода. Функциональность системы
разделяется на отдельны е уровни и модули, каждый из которых отвечает за строго
определённую область задач.
Архитектурные уровни приложения включают слой представления, слой бизнес -
логики, слой доступа к данным и слой базы данных.
Слой представления (Presentation Layer) отвечает за взаимодействие пользователя с
системой и обработку HTTP-запросов. В его состав входят FastAPI -роутеры, Django views
и HTML-шаблоны, формы ввода данных, маршруты приложения, а также Pydantic -схемы
для проверки входящих данных.
Слой бизнес-логики (Business Logic Layer) отвечает за реализацию основных правил
работы системы и обработку пользовательских сценариев. В данном слое располагаются
контроллеры, сервисы, механизмы проверки бизнес-правил и обработка ролевого доступа.
Сервисный слой отвечает за добавле ние и редактирование объектов недвижимости,
управление фотографиями и документацией, оформление договоров купли -продажи,
ведение истории договоров пользователей и проверку уникальности данных.
Слой доступа к данным (Data Access Layer) отвечает за взаимодействие приложения
с базой данных PostgreSQL. В его состав входят ORM -модели, сессии базы данных и
репозитории для работы с сущностями.
Слой базы данных (Database Layer) обеспечивает хранение инф ормации обо всех
сущностях системы. В PostgreSQL предполагается хранение учётных записей
пользователей, данных об объектах недвижимости и их характеристиках, фотографий,
строительной документации, договоров купли-продажи .
2.5. Проектные решения по реализации тестирования приложения
Тестирование информационной системы АРМ застройщика рассматривается как
отдельный этап контроля качества, направленный на подтверждение корректности работы
пользовательских сценариев, API -маршрутов и мех анизмов разграничения доступа.
Проверке подлежат как отдельные компоненты системы, так и взаимодействие между
Django-интерфейсом и FastAPI-бэкендом.
Основными целями тестирования являются:
– проверка корректности работы пользовательских сценариев;
– подтверждение работоспособности REST API;
– проверка обработки JWT-токенов и ролевой модели доступа;
– выявление ошибок валидации входных данных;
– контроль корректности HTTP-статусов и сообщений об ошибках;
– проверка взаимодействия веб-интерфейса и API;
– обеспечение стабильности системы при изменении функциональности.
Для проекта используется комбинированная стратегия тестирования, включающая
функциональное, интеграционное, UI-, API-, негативное и регрессионное тестирование.

3.1. Стек технологий

Backend (основной язык и фреймворки):
– Python 3.11+ — основной язык разработки всех компонентов системы.
– FastAPI — асинхронный веб-фреймворк для реализации REST API (бизнес-логика, обработка запросов, автоматическая документация Swagger/ReDoc).
– Django 5.x — веб-фреймворк для пользовательского интерфейса (шаблоны, формы, маршрутизация). Django выступает HTTP-клиентом к FastAPI и не хранит доменные данные в своей БД.
– SQLModel — ORM поверх SQLAlchemy для работы с PostgreSQL в FastAPI-части.
– Pydantic — валидация данных и сериализация схем запросов и ответов.

База данных:
– PostgreSQL — реляционная СУБД для централизованного хранения данных.
– psycopg2 / asyncpg — драйверы подключения к PostgreSQL.

Аутентификация и безопасность:
– JWT (JSON Web Tokens) — механизм аутентификации.
– python-jose — создание и проверка JWT-токенов.
– passlib (Argon2) — хеширование паролей пользователей.
– OAuth2 Password Flow — встроенная схема авторизации FastAPI.

Тестовая инфраструктура:
– pytest — фреймворк для запуска тестов.
– pytest-asyncio — асинхронные тесты FastAPI.
– httpx — HTTP-клиент для API-тестов.
– Selenium — E2E-тестирование Django-интерфейса (tests/e2e, Page Object Model).

Дополнительные библиотеки:
– python-dotenv, pydantic-settings — конфигурация окружения.
– email-validator — проверка email при регистрации.
– requests — HTTP-запросы из Django к FastAPI.
– python-docx — генерация договоров купли-продажи в формате Word (.docx).
– Pillow — обработка изображений при загрузке фотографий.
– fastapi-pagination — пагинация списков в API v2.

3.2. ERD-модель информационной системы

Физическая модель базы данных представлена в виде ERD-диаграммы (Entity-Relationship Diagram), реализованной средствами СУБД PostgreSQL. Диаграмма отражает структуру таблиц, их атрибуты, первичные и внешние ключи, а также связи между сущностями.

Рисунок 2 — Схема базы данных

База данных информационной системы включает 7 взаимосвязанных таблиц: role, user, propertytype, realestateobject, photo, document, contract.

Таблица role содержит справочник ролей системы (admin, manager, user). Таблица user хранит учётные записи пользователей с привязкой к роли. Таблица propertytype — справочник типов объектов недвижимости (квартира, дом, коммерческая площадь и т.д.). Таблица realestateobject является центральной и содержит характеристики продаваемых объектов. Таблица photo хранит метаданные и пути к файлам фотографий объектов. Таблица document содержит строительную документацию (схемы, планы застройки). Таблица contract хранит сведения о договорах купли-продажи и путь к сгенерированному файлу .docx.

3.4. Алгоритмы

В данном разделе описаны ключевые алгоритмы информационной системы АРМ застройщика. Графическое отображение в виде блок-схем вынесено в Приложение Б (файл plantuml_diagrams.puml).

3.4.1. Алгоритм авторизации и выдачи JWT (FastAPI + Django)

Реализован в app/controllers/auth_controller.py и представлении login_view (Django). (см. Приложение Б, рисунок Б.1)

Последовательность действий:
– Пользователь открывает GET /login/ и вводит email и пароль.
– Django отправляет POST на /api/v2/auth/login (form-data: email, password).
– AuthController ищет пользователя в таблице user по email.
– При отсутствии пользователя или неверном пароле возвращается 401 Unauthorized.
– Пароль проверяется через Argon2 (passlib). При успехе формируется access_token (JWT).
– Django сохраняет access_token и role_name в session, загружает профиль через GET /api/v2/auth/me.
– Выполняется redirect на /catalog/ (единая точка входа для всех ролей; разделы admin/manager доступны из меню по роли).
– Защищённые запросы Django передают заголовок Authorization: Bearer <access_token>.

3.4.2. Алгоритм добавления объекта недвижимости с фотографиями (администратор)

Реализован в admin_property_create_view и PropertyController. (см. Приложение Б, рисунок Б.2)

Последовательность действий:
– Администратор авторизуется (роль admin, декоратор require_admin).
– Переходит на /admin_panel/properties/create/.
– Заполняет форму PropertyForm: тип объекта, площадь, этаж, отделка, материал стен, цены, адрес, описание.
– Django отправляет POST /api/v2/properties/ с JSON-телом.
– FastAPI валидирует данные (Pydantic), создаёт запись в realestateobject со статусом «в продаже».
– При успехе — redirect на список объектов или загрузку фото через /admin_panel/media/photos/.
– Фотографии загружаются multipart POST /api/v2/photos/ с привязкой к property_id; файлы сохраняются в uploads/.

3.4.3. Алгоритм формирования договора купли-продажи (Word .docx)

Реализован в ContractController и manager_generate_contract_view / contract_download_view. (см. Приложение Б, рисунок Б.3)

Последовательность действий:
– Менеджер или администратор открывает /manager/contracts/generate/ или панель договоров.
– Указывает объект недвижимости, покупателя (user_id), дату и статус договора.
– Django вызывает POST /api/v2/contracts/ для создания записи в contract.
– Для генерации файла вызывается эндпоинт формирования .docx (python-docx): подставляются реквизиты объекта, стороны, цена.
– Путь к файлу сохраняется в generated_file_path; пользователь скачивает договор через /account/contracts/<id>/download/ или панель менеджера.
– При ошибке API Django выводит краткое сообщение через messages.error (format_api_detail).

3.5. Документация по работе с информационной системой

3.5.1. Документация по работе с API

API реализован на FastAPI с версионированием:
– /api/v1/ — базовая версия (полный CRUD, аутентификация);
– /api/v2/ — версия, используемая Django-клиентом (пагинация fastapi-pagination, улучшенные схемы).

Основные группы эндпоинтов (префиксы относительно версии):
– /auth/login, /auth/register, /auth/logout, /auth/me — аутентификация и профиль;
– /properties — CRUD объектов недвижимости, фильтрация, смена статуса;
– /property-types — справочник типов (admin);
– /photos — загрузка и удаление фотографий;
– /documents — строительная документация по объекту;
– /contracts — договоры, генерация .docx.

Аутентификация: JWT Bearer. После POST /auth/login клиент получает access_token. Заголовок: Authorization: Bearer <token>.

Защита эндпоинтов: зависимости get_current_user, проверка роли admin/manager/user.

Интерактивная документация (offline Swagger, сервер FastAPI на порту 8000):
– http://127.0.0.1:8000/api/v1/docs — Swagger UI (схема v1);
– http://127.0.0.1:8000/api/v2/docs — Swagger UI (схема v2);
– OpenAPI: /api/v1/openapi.json и /api/v2/openapi.json.

Публичные без токена: GET /properties, GET /properties/{id}, GET /photos, GET /documents/{property_id}, POST /auth/register, POST /auth/login.

Подробный перечень с примерами JSON — в файле API_ENDPOINTS_DOCUMENTATION.txt в корне проекта.

3.5.2. Документация по работе с веб-приложением

Веб-приложение реализовано на фреймворке Django 5.x и функционирует как клиент к REST API FastAPI. Django не хранит доменные данные в своей базе: все операции чтения и записи выполняются через модуль app/services/api_client.py, который отправляет HTTP-запросы к API версии v2 (базовый адрес задаётся переменной API_BASE_URL, по умолчанию http://127.0.0.1:8000/api/v2).

После успешного входа в сессии Django сохраняются:
  • access_token — JWT-токен для заголовка Authorization при запросах к API;
  • token_type — обычно bearer;
  • role_name — имя роли (admin, manager, user), извлекается из токена;
  • user_info — данные профиля с эндпоинта GET /api/v2/auth/me.

При ответе API со статусом 401 (истёкший или недействительный токен) сессия сбрасывается, пользователю выводится сообщение об ошибке и выполняется перенаправление на страницу входа. Уведомления об успешных операциях и ошибках отображаются через стандартный механизм django.contrib.messages (всплывающие блоки в шаблоне partials/messages.html). Тексты ошибок API сокращаются функцией format_api_detail() до понятных фраз на русском языке (некорректный email, короткий пароль и т.д.).

Базовый URL веб-приложения (локально): http://127.0.0.1:8001/

2. Авторизация и регистрация

2.1. Вход в систему

GET /login/ — отображение формы входа (поля: email, пароль). Ссылка на регистрацию и напоминание о смене пароля в профиле.

При отправке формы (POST /login/) Django вызывает ApiClient.login(), который отправляет на FastAPI запрос POST /api/v2/auth/login (form-data: username=email, password). При успехе:
  • токен и роль сохраняются в session;
  • загружается профиль через GET /api/v2/auth/me;

  • выполняется redirect на /catalog/ (единая точка входа для всех ролей).

При неверных данных пользователь остаётся на странице входа, вверху отображается краткое сообщение об ошибке (например, «Неверный email или пароль»), без технических деталей JSON.

3.5.3. Руководство по развёртыванию проекта

В данном разделе приведена пошаговая инструкция развёртывания информационной системы «АРМ застройщика» на локальном компьютере под управлением ОС Windows (аналогичные шаги применимы для Linux/macOS с заменой путей активации venv).

Требования к программному обеспечению:
  • Python 3.10 или выше;
  • PostgreSQL 14+ (рекомендуется 17+);
  • Git (опционально, для клонирования репозитория);
  • браузер Google Chrome, Mozilla Firefox или Microsoft Edge (для работы и E2E-тестов);
  • два свободных TCP-порта: 8000 (FastAPI) и 8001 (Django).

Шаг 1. Установка PostgreSQL и создание базы данных

1.1. Скачайте дистрибутив PostgreSQL с официального сайта https://www.postgresql.org/download/ и выполните установку.
1.2. Запомните пароль суперпользователя postgres.
1.3. Создайте базу данных для проекта (через pgAdmin или psql):

CREATE DATABASE tverdov_api_db;

Важно: API_BASE_URL должен указывать на порт 8000 (FastAPI), а не 8001.

4.6. Примените миграции Django (служебные таблицы сессий и админки Django):
python manage.py migrate

4.7. Запустите веб-сервер на порту 8001:
python manage.py runserver 8001

4.8. Откройте в браузере: http://127.0.0.1:8001/


Шаг 5. Проверка работоспособности

5.1. Убедитесь, что оба процесса запущены без ошибок (терминалы FastAPI и Django).
5.2. Откройте http://127.0.0.1:8001/catalog/ — должен отобразиться каталог (возможно пустой до добавления объектов).
5.3. Выполните вход под учётной записью admin@example.com / password123 (или зарегистрируйте нового пользователя).
5.4. Проверьте разделы «Объекты CRM», «Менеджер», «Кабинет» в зависимости от роли.
5.5. Создайте тестовый объект, загрузите фото, смените статус, сформируйте договор и скачайайте .docx.
5.6. (Опционально) Запустите автотесты из корня проекта:
pytest tests/api
pytest tests/e2e -m e2e


Примечания по эксплуатации

  • При ответе API 401 Django сбрасывает сессию и перенаправляет на /login/.
  • Остановка серверов: Ctrl+C в каждом терминале.
  • Каталог uploads/ должен быть доступен на запись для загрузки фото и документов.
  • При смене хоста или порта FastAPI обновите API_BASE_URL в .env Django.

ЗАКЛЮЧЕНИЕ

В ходе выполнения курсового проекта разработана и протестирована информационная система «АРМ застройщика», предназначенная для автоматизации учёта объектов недвижимости, управления фотографиями и строительной документацией, ведения статусов продаж и оформления договоров купли-продажи.

В рамках проекта созданы два взаимосвязанных приложения: REST API на FastAPI (версии v1 и v2) с хранением данных в PostgreSQL и веб-клиент на Django, использующий API v2 для всех операций с данными. Реализована ролевая модель доступа (admin, manager, user) и сценарии для неавторизованных посетителей (просмотр каталога).

Реализованы ключевые функции: регистрация и JWT-аутентификация (Argon2), CRUD объектов и справочника типов, загрузка фото и документов, смена статусов и бронирование, генерация договоров в формате Word (.docx), администрирование пользователей. Для API предусмотрена автоматическая документация Swagger (offline).

Тестирование включало 86 API-тестов и 25 E2E-тестов на Selenium; все прогоны завершены успешно. Дефекты промежуточных версий устранены в API v2.

Разработанная система соответствует техническому заданию и может быть рекомендована к опытной эксплуатации и дальнейшему развитию (мобильный клиент, расширенная отчётность, интеграция с внешними CRM).

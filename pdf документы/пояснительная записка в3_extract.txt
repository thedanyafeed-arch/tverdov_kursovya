ВВЕДЕНИЕ 
В настоящее время автоматизация деятельности организаций является одним из 
ключевых направлений развития информационных технологий. Особенно актуально 
использование информационных систем для фитнес -центров, работа которых связана с 
обработкой большого объёма данных о клиентах, тренировках, расписании занятий и 
персонале. Использование ручного учёта или разрозненных программных решений снижает 
эффективность работы сотр удников, увеличивает время обработки информации и повышает 
вероятность возникновения ошибок. В связи с этим разработка автоматизированного рабочего 
места фитнес -центра является актуальной задачей, направленной на повышение качества 
управления и обслуживания клиентов. 
Целью курсового проекта является разработка и тестирование информационной системы 
для автоматизации деятельности фитнес -центра. Для достижения поставленной цели 
необходимо выполнить анализ предметной области, определить требования к системе, 
разработать архитектуру приложения, реализовать основные функции веб -приложения и API -
бэкенда, а также провести тестирование разработанной системы. 
Объектом исследования является процесс автоматизации деятельности фитнес -центра. 
Предметом исследования выступ ают методы и технологии проектирования, разработки и 
тестирования клиент-серверных информационных систем. 
Разрабатываемая система предназначена для хранения и обработки данных 
пользователей, управления тренировками, расписанием и взаимодействием между клие нтами, 
тренерами и администраторами. Использование веб -технологий и клиент -серверной 
архитектуры позволяет обеспечить централизованный доступ к системе и возможность 
дальнейшего расширения её функциональности. 
Практическая значимость работы заключается в с оздании информационной системы, 
способной повысить эффективность работы фитнес -центра, упростить обработку данных и 
автоматизировать основные процессы организации. 
Структура курсового проекта включает введение, аналитическую часть, проектную 
часть, раздел тестирования, заключение, список источников и приложения.

ВИД АВТОМАТИЗИРУЕМОЙ ДЕЯТЕЛЬНОСТИ 
Приложение предназначено для клиентов фитнес-центра. Цель приложения – 
создание фитнес – расписания тренерами и контроль за соблюдением выполнения 
предписанных тренировок клиентами . 
Предполагается, что в системе фитнес центра будут определены следующие роли 
пользователей: клиенты, тренеры, менеджеры, администраторы. 
Регистрацию тренеров в АРМ выполняет администратор. Для того, чтобы 
зарегистрировать тренера нужно указать: ФИО, фото, пол, стаж работы, список 
достижений. Регистрацию новых клиентов клуба ведут менеджеры. Для того, чтобы 
зарегистрировать клиента нужно указать: ФИО, телефон, пароль, дату рождения, фото, 
пол. Постоянным клиентам менеджеры могут предоставлять скидки на тренировки. 
Любой клиент после авторизации (авторизация происходит по номеру телефона и 
паролю) может выбрать себе тренера (если у него нет такового). В этом случае клиент 
видит список тренеров с именем, фото, полом, стажем работы и списком достижений. 
Клиент может отправить заявку любому из тренеров, написав при этом цель, которую он  
хочет достигнуть при тренировках. 
Тренер после авторизации видит новые заявки от клиентов и их количество (если 
таковые имеются). Тренер может принять заявку или отклонить. В случае отказа, тренер 
должен указать причину. В случае подтверждения заявки тренер должен выставить план 
индивидуальных занятий для клиента. Выбрав из списка клиентов без плана тренировок, 
тренер видит цель клиента, его возраст и планирует даты тренировочного цикла. Для 
индивидуальных занятий тренер может выбрать упражнения, указывая при этом его вид 
(приседания, отжимания и т.д.), частоту выполнения (сколько раз в неделю), число  
подходов и число повторений в каждом подходе. 
Клиент, отправивший заявку, но не получивший ответа, видит список своих заявок с 
результатами (в том числе с указанием причины при отказе) и количеством дней 
ожидания ответа. Получив план тренировок, клиент видит экран с 2 вклад ками: план  
тренировок (датасписок упражнений) и сегодняшний перечень индивидуальных занятий. 
Для последней  выводится список: вид упражнения, количество повторов и «флажок», 
позволяющий отметить  выполнено ли упражнение. Несмотря на это, упражнение не 
будет засчитано системой до тех пор, пока клиент не укажет показатель своего пульса во 
время выполнения упражнения. 
Сверху выводится сегодняшний прогресс (по количеству выполненных упражнений) в  
процентах с графическим отображением.  Тренер также может посмотреть  список своих 
текущих клиентов с указанием у каждого: процента выполнения всего цикла тренировок 
(зависит от длительности цикла) и  процента выполненных упражнений (т.к. некоторые 
упражнения могут быть пропущены). По  каждому клиенту выводится средний 
показатель пульса во время выполнения упражнений. 
Приложение может выполнять генерацию следующих отчетов (Word/Excel): 
− Для фитнес-тренеров (список клиентов, расписание тренировок); 
− Для клиентов фитнес-центра (план тренировок на сегодняшний день, расписание 
тренировок на неделю)

2. АНАЛИТИЧЕСКАЯ ЧАСТЬ 
2.1. Цели, функции и задачи системы 
Актуальность разработки автоматизированного рабочего места фитнес -центра 
обусловлена необходимостью повышения эффективности управления внутренними 
процессами организации в условиях постоянного увеличения объёма данных и 
количества пользователей. В процессе работы фитнес -центра ежедневно выполняются 
операции, связанные с регистрацией клиентов, управлением расписанием тренировок, 
формированием тренировочных программ, обработкой заявок и контролем доступа 
пользователей к различным функциям системы. При использовании ручного учёта или 
разрозненных программных решений возрастает вероятность ошибок, усложняется 
контроль данных и увеличивается нагрузка на сотрудников фитнес-центра. 
 
Основной целью разрабатываемой системы является создание единого программного 
комплекса, который позволит автоматизировать основные процессы фитнес -центра, 
обеспечить централизованное хранение информации и повысить удобство 
взаимодействия между клиентами, тренерам и и администрацией. Предполагается, что 
система будет обеспечивать безопасную обработку данных, поддержку ролевой модели 
доступа и возможность дальнейшего расширения функциональности. 
 
Информационная система будет включать несколько основных компонентов. О дним из 
компонентов станет API-бэкенд с поддержкой версионирования API (v1 и v2). API будет 
использоваться для обработки запросов, взаимодействия с базой данных, реализации 
бизнес-логики и поддержки механизмов аутентификации и авторизации пользователей. 
Для API предполагается использование автоматической документации Swagger/OpenAPI. 
 
Вторым компонентом системы станет полнофункциональное веб -приложение, 
реализуемое на основе Django. Веб -приложение будет использовать шаблоны, формы и 
административную панель для взаимодействия с пользователями. Получение и 
обработка данных будут выполняться через REST API, что позволит разделить 
пользовательский интерфейс и серверную бизнес-логику. 
 
Для хранения информации предполагается использование клиент -серверной базы 
данных PostgreSQL, обеспечивающей централизованное хранение данных 
пользователей, расписания тренировок, заявок и тренировочных программ. 
К основным функциям системы относятся: 
− регистрация и авторизация пользователей; 
− управление ролями и правами доступа; 
− хранение и обработка данных клиентов; 
− создание тренировочных программ; 
− управление расписанием тренировок; 
− обработка заявок на занятия; 
− взаимодействие между клиентами и тренерами; 
− администрирование системы.

системе фитнес-центра.

2.2. Описание предметной области системы 
Предметная область проекта охватывает деятельность фитнес-центра в части управления 
клиентами, организации тренировочного процесса, формирования тренировочных программ и 
контроля взаимодействия между пользователями системы. Анализ предметной области 
выполняется не только как описание сущностей базы данн ых, но и как исследование основных 
процессов работы фитнес-центра, требующих автоматизации. 
В основу проектирования системы предполагается положить последовательность 
основных этапов взаимодействия пользователей: 
регистрация пользователя → выбор тренера → подача заявки на тренировку → 
формирование тренировочного плана → выполнение тренировок → отслеживание прогресса → 
формирование отчетности. 
Именно данный процесс определяет состав сущностей и взаимосвязей внутри системы. 
Основная задача проектирования закл ючается в обеспечении непрерывности хранения и 
обработки данных на всех этапах работы пользователей с приложением. 
С точки зрения информационных потоков в системе предполагается выделение 
следующих основных объектов предметной области: 
− Клиент - персональные данные, контактная информация, история тренировок и 
показатели прогресса; 
− Тренер - данные о специализации, расписании и закрепленных клиентах; 
− заявка на тренировку - дата создания, статус заявки, выбранный тренер; 
− Тренировочный план - набор упражнений, р асписание занятий, параметры 
тренировок; 
− Отчет о тренировках - информация о выполненных упражнениях и достигнутых 
результатах; 
− Пользователь системы - учетные данные, роль и права доступа. 
 
Выделение именно этих сущностей обусловлено спецификой работы фитне с-центра и 
необходимостью централизованного хранения информации о тренировочном процессе. 
В предметной области предполагается использование нескольких ролей пользователей: 
− Администратор - управление тренерами и учетными записями; 
− Менеджер - работа с клиентской базой и заявками; 
− Тренер - создание тренировочных программ и контроль прогресса клиентов; 
− Клиент - просмотр тренировок, отметка выполненных упражнений и отслеживание 
результатов. 
 
Такое разделение ролей позволит ограничить доступ пользователей только к тем 
функциям и данным, которые относятся к их обязанностям. Для реализации данного механизма 
предполагается использование ролевой модели доступа (RBAC). 
 
Для формирования структуры проекта предполагается изучение существующих 
информационных систем фитнес -центров, CRM -систем и веб -приложений для управления 
тренировочным процессом. Также будут анализироваться процессы взаимодействия между 
сотрудниками фитнес -центра и клиентами, структура тренировочных программ и принципы 
хранения пользовательских данных.

Проблемы предметной области и обоснование автоматизации 
При отсутствии едино й информационной системы в работе фитнес -центра возникают 
типовые проблемы: 
− разрозненное хранение информации о клиентах и тренировках; 
− сложность отслеживания прогресса клиентов; 
− необходимость повторного ручного ввода данных; 
− ошибки при работе с расписанием и заявками; 
− сложность взаимодействия между сотрудниками и клиентами; 
− отсутствие централизованного контроля тренировочного процесса. 
 
Автоматизация данных процессов позволит сократить количество рутинных операций и 
повысить эффективность работы фитнес-центра. 
Реализация информационной системы должна обеспечить: 
− централизованное хранение данных; 
− единые сценарии обработки информации; 
− разграничение прав доступа пользователей; 
− взаимосвязь между клиентами, тренерами, тренировочными планами и заявками; 
− повышение скорости обработки информации и качества обслуживания клиентов.

пользователей, которым необходимо быстро выполнять рабочие операции и получать 
доступ к нужной информации без сложной навигации.

2.4. Проектные решения по реализации внутренней архитектуры приложения 
В проекте планируется использование двухслойной архитектуры: Django применяется 
как web-слой пользовательского взаимодействия, а FastAPI - как сервисный слой бизнес-
логики и REST API. Такое решение позволяет разделить ответственность между 
интерфейсной частью и обработкой данных: web -слой отвечает за отображение страниц, 
формы, маршрутизацию и взаимодействие с пользователем, а API -слой - за обработку 
бизнес-операций, проверку ролей, валидацию данных и работу с базой данных. 
 
Взаимодействие компонентов системы организуется по следующей схеме: 
пользователь → Django web-приложение → FastAPI REST API → PostgreSQL. 
 
Внутренняя архитектура проекта строится на основе модульного подхода. 
Функциональность системы разделяется на отдельные уровни и модули, каждый из 
которых отвечает за строго определенную область задач. Такой подход позволяет 
обеспечить слабую связанность компонентов, высокую читаемость кода и возможность 
независимого развития отдельных частей приложения. 
 
Использованный стек технологий 
− Python 3.11+ - основной язык разработки всех компонентов системы; 
− Django - серверный web-интерфейс, шаблоны, формы, маршруты и административная 
панель; 
− FastAPI - REST API, обработка запросов, Redoc/Swagger-документация; 
− PostgreSQL - клиент-серверная база данных; 
− SQLModel + Pydantic - модели данных, ORM, типизация и валидация запросов; 
− JWT (python-jose / bcrypt) - аутентификация и разграничение доступа; 
− Requests - взаимодействие Django-приложения с FastAPI; 
− Selenium + Pytest - автоматизированное тестирование пользовательских сценариев

3.1. ERD-модель информационной системы 
Физическая модель базы данных представлена в виде ERD -диаграммы (Entity -

3.3 Алгоритмы 
В данном разделе описаны ключевые алгоритмы, реализованные в информационной 
системе фитнес -центра. Каждый алгоритм представлен словесным описанием 
последовательности действий, а его графическое отображение в виде блок‑схемы 
вынесено в Приложение Б. 
 
3.3.1 Алгоритм авторизации и выдачи JWT (FastAPI) 
Алгоритм обеспечивает аутентификацию пользователя по номеру телефона (или email) и 
паролю с последующей выдачей пары JWT‑токенов ( access и refresh). Реализован в 
контроллере AuthController. (см. Приложение Б, рисунок 13) 
Последовательность действий: 
1. Клиент (веб‑приложение Django) отправляет POST‑запрос на эндпоинт 
/api/v1/auth/login с полями username (номер телефона) и password. 
2. Контроллер выполняет поиск пользователя в таблице users по полю phone: 
3. Если пользователь не найден – возвращается статус 401 Unauthorized с сообщением 
«Неверный телефон или пароль». 
4. Если найден – с помощью bcrypt проверяется соответствие переданного пароля хэш у 
password_hash в базе данных. 
5. При несовпадении пароля – возвращается 401. 
6. При успешной проверке генерируются: 
access_token (срок жизни 30 минут, содержит sub = user_id и role); 
refresh_token (срок жизни 24 часа). 
7. Токены упаковываются в JSON и возвращаются клиенту. 
8. Клиент сохраняет токены (в Django – в сессии, в API‑клиенте – в localStorage или 
куках). 
9. Во всех последующих запросах к защищённым эндпоинтам клиент передаёт 
access_token в заголовке Authorization: Bearer <token>. 
10. Зависимость get_current_user в F astAPI декодирует токен, извлекает user_id, 
загружает объект пользователя из БД и проверяет его роль. При истекшем токене 
возвращается 401. 
 
3.3.2 Алгоритм обработки заявки клиента на тренировку 
Алгоритм описывает процесс создания заявки клиентом, её просм отра тренером и 
последующего принятия или отклонения с указанием причины. Реализован в 
контроллерах ApplicationsController и TrainersController. (см. Приложение Б, рисунок 14) 
Последовательность действий: 
1. Клиент авторизуется в системе (роль client). 
2. Переходит в раздел «Выбор тренера». 
3. Видит список тренеров с ФИО, фото, стажем и достижениями. 
4. Выбирает тренера, нажимает «Отправить заявку». 
5. Заполняет поле «Цель тренировок» (обязательное). 
6. Отправляет POST‑запрос на /api/v1/applications/ с полями trainer_id, goal. 
Сервер создаёт запись в таблице applications со статусом pending (в ожидании), 
фиксирует created_at. 
7. Возвращает клиенту сообщение об успешной отправке.

Алгоритм позволяет тренеру после принятия заявки создать индивидуальн ый план 
тренировок для клиента, включающий упражнения с заданием количества подходов, 
повторений и частоты выполнения.  
Последовательность действий: 
1. Тренер открывает карточку клиента (после принятия заявки или из списка «Мои 
клиенты»). 
2. Нажимает кнопку «Создать тренировочный план». 
3. Система открывает форму, в которой необходимо указать: 
4. Даты начала и окончания плана (период действия). 
5. После сохранения плана появляется возможность добавлять упражнения. 
6. Для каждого упражнения тренер заполняет: 
− Название (например, «Приседания», «Отжимания»); 
− Количество повторений (repetitions); 
− Количество подходов (sets); 
− Частоту выполнения в неделю (per_week); 
− Дополнительные заметки (notes). 
7. При отправке формы POST‑запрос на /api/v1/workout -plans/{plan_id}/exercises/ 
создаёт запись в таблице workout_exercises, привязанную к плану. 
8. Тренер может добавить несколько упражнений. План считается активным, когда 
добавлено хотя бы одно упражнение. 
9. Клиент получает доступ к своему плану тренировок (вкладки «План тренировок» и 
«Сегодняшние упражнения»). 
10. Система автоматически разбивает упражнения по дням согласно частоте per_week и 
датам плана (логика распределения реализована в сервисном слое).

− название, количество подходов и повторений;

3.4.1. Документация по работе с API 
API версионируется через префикс пути: /api/v1/ (базовая версия). В ходе тестирования

сохранением обратной совместимости. 
Версионирование: 
v1 – первоначальная реализация, включающая полную поддержку пагинации, 
фильтрации, ролевой  модели (client, trainer, manager, admin), JWT -аутентификацию и все 
требуемые эндпоинты.  
Поддержка стандартных HTTP-методов 
Для основных сущностей (клиенты, тренеры, заявки, тренировочные планы) 
реализованы стандартные HTTP-методы: 
− Метод GET с эндпоинтом /api/v1/clients/trainers с параметрами пагинации ?page=1&size=10 
возвращает список объектов. 
− Метод GET с эндпоинтом /api/v1/managers/clients/{id} позволяет просмотреть один объект 
по его идентификатору. 
− Создание нового объекта выполняется методом POST на э ндпоинт 
/api/v1/clients/applications. 
− Полное обновление объекта осуществляется методом PUT на /api/v1/managers/clients/{id}. 
− Частичное обновление (например, скидки клиента) реализовано через метод PATCH на 
эндпоинте /api/v1/managers/clients/{id}/discount. 
− Удаление объекта (деактивация) производится методом DELETE на 
/api/v1/managers/clients/{id}. 
 
Аутентификация и авторизация. 
Используется JWT (Bearer). После успешного входа сервер возвращает access_token 
(время жизни 60 минут) и refresh_token. 
Токен передаётся в заголовке: Authorization: Bearer <access_token>. 
В Swagger UI реализована кнопка «Authorize» для ввода токена.

Аутентификация Процесс проверки подлинности пользователя (например, 
по паре логин/пароль). 
Авторизация Процесс предоставления доступа к ресурсам после 
успешной аутентификации на основе роли. 
Access token Короткоживущий JWT-токен, подтверждающий личность 
пользователя и его права. 
Refresh token Долгоживущий JWT-токен, используемый для получения 
новой пары токенов без повторного ввода пароля. 
Перевозчик Организация или индивидуальный предприниматель, 
владеющие транспортными средствами и 
обслуживающие маршруты общественного транспорта. 
Маршрут Установленный путь следова ния транспортного средства 
между начальной и конечной остановками, имеющий 
уникальный номер, тип транспорта и расписание. 
Остановка Место на маршруте, оборудованное для посадки и 
высадки пассажиров. Характеризуется названием, 
адресом и наличием павильона. 
Рейс Конкретное отправление транспортного средства по 
определённому маршруту в заданные дату и время. 
Статус рейса Состояние рейса в ходе его выполнения: запланирован, 
отправлен, задержан, отменён, завершён. 
Табель рабочего времени Документ, фиксирующий выходы на работу сотрудников 
(водителей и кондукторов) с указанием количества 
отработанных дней и часов.

ЗАКЛЮЧЕНИЕ 
В ходе выполнения проекта была разработана и протестирована информационная 
система АРМ «Фитнес‑центр», полностью соответствующая техническому заданию. 
Разработана серверная часть в виде REST API на базе FastAPI с использованием SQLModel, 
PostgreSQL и JWT‑аутентификации. API имеет единственную версию v1, так как в ходе 
тестирования дефектов, требующих обратно несовместимых изменений, не выявлено; 
реализованы пагинация, фильтрация, ролевой доступ (RBAC), автоматическая документация 
Swagger/ReDoc. Разработано веб‑приложение на Django, которое выступает клиентом к API. 
Реализованы все сценарии для клиентов, тренеров, менеджеров и администраторов: выбор 
тренера, создание и обработка заявок, формирование тренировочных планов с упражнениями, 
отслеживание прогресса с фиксацией пульса, выгрузка отчётов (Word/Excel), а также 
CRUD‑операции с клиентами и тренерами. Организовано тестовое окружение: написаны 
автоматизированные API и Django тесты (pytest), UI‑тесты (Selenium), использованы фикстуры. 
Выполнено интеграционное тестирование, дефектов не выявлено. Подготовлена полная 
документация: ERD‑модель, файловая структура, описание алгоритмов, руководство 
пользователя, руководство по развертыванию, глоссарий, список источников. 
Направления дальнейшего развития: 
− Добавление мобильного клиента с использованием существующего API. 
− Внедрение уведомлений (email/SMS) о статусе заявок и тренировках. 
− Расширение отчётности (анализ посещаемости, эффективности тренировок, 
подключение фитнес‑трекеров). 
 
Таким образом, цели курсового проекта достигнуты, результаты могут быть 
использованы как учебный пример интеграции Django и FastAPI, а также как основа для 
реального внедрения в небольших фитнес‑центрах.
